# ۰۷ — اتصال به پنل پشتیبان، گزارش‌ها و ماسک لاگ (Back + Panel)

**وابستگی:** HW-05. **پیش‌نیاز:** ماسک لاگ (HW-7.3) باید **قبل از** اولین استفادهٔ واقعی از پنل مالی deploy شود. پس HW-7.3 همراه HW-05 منتشر می‌شود.
**خروجی:** کارت فقط‌خواندنی وضعیت مالی در میز کار پشتیبان، گزارش مانده و مغایرت بانک، و ماسک شبا در `admin_activities`.

## HW-7.1 — کارت فقط‌خواندنی در میز کار پشتیبان

- **Back:** فیلد `finance` در `GET /admin/reserve-support/:id` (RS-5.3) پر شود:

```ts
finance: {
  guest_paid, fee_amount, host_amount,       // from the snapshot
  canceled: { refund_amount, host_amount } | null,
  wallet_status: 'PENDING'│'AVAILABLE'│'ON_HOLD'│'PROCESSING'│'SETTLED'│'PARTIAL'│null,
  stages: [{ seq, amount, release_at, bucket }],   // HW-2.5
  handover: { guest_checked_in_at, complaint_window_ends_at, complaint_status } | null,  // HW-09
  release_at,
  host_bank_verified: boolean,               // yes/no only, never the IBAN
  refund: { status, amount } | null,         // GuestRefund, for 130 and 140
} | null
```

- این داده از سرویس کیف پول خوانده می‌شود. ماژول پشتیبان هیچ endpoint مالی صدا نمی‌زند و نقش پشتیبان هیچ دسترسی به ماژول‌های مالی ندارد. تست: درخواست نقش پشتیبان به `admin/settlements` خطای 403 می‌گیرد، ولی `finance` در جزئیات رزرو پر است.
- **Panel:** کارت «وضعیت مالی این رزرو» با برچسب «فقط مشاهده» در ستون کناری `Panel/app/reserve-support/show/[id]/page.tsx`. شامل پرداخت مهمان، سهم جایاب، طلب میزبان، وضعیت، «شبای میزبان: تأییدشده / تأیید نشده» و وضعیت بازگشت وجه. اگر شبا تأیید نشده، یک متن راهنما نمایش داده شود: «در تماس، میزبان را به تکمیل اطلاعات تسویه در پروفایل راهنمایی کنید.»

## HW-7.2 — گزارش مانده و مغایرت

`GET /admin/settlements/report?from=&to=` و نسخهٔ Excel آن (`.../report/excel`) با الگوی موجود Excel در Back (`STORAGE_EXCEL` در `Back/src/common/utils/constants/storage-folders.ts` و استفاده در `tasks.service.ts`):

| بخش | محتوا |
| --- | --- |
| مانده‌ها | جمع هر bucket برای همهٔ میزبانان، و فهرست ۲۰ میزبان با بیشترین «قابل تسویه» |
| واریزهای بازه | حواله‌های `SETTLED` و بازگشت‌های `REFUNDED` با تاریخ واریز، حساب مبدأ، شمارهٔ پیگیری و مبلغ، برای تطبیق با صورت‌حساب بانک |
| مغایرت‌ها | حواله‌ها و بازگشت‌های `PROCESSING` قدیمی‌تر از ۳ روز، «قابل تسویه» با شبای تأییدشده قدیمی‌تر از ۷ روز، `GuestRefund` در `AWAITING_INFO` قدیمی‌تر از ۳ روز |
| گزارش‌های تحویل (HW-09) | تعداد گزارش به ازای هر ۱۰۰ رزرو، به تفکیک دسته و میزبان. میانهٔ زمان رسیدگی و تعداد گزارش‌های بیشتر از ۲۴ ساعت (D13). جمع بازگشت جزئی. نسبت «بدون اثر» و «رد». هدف کارفرما این است که پرونده‌های پشتیبانی زیاد نشوند. |
| سلامت دفترکل | رزروهایی که جمع bucketهایشان با `host_amount` snapshot منهای اصلاحیه‌ها برابر نیست. باید همیشه خالی باشد و هر ردیف یعنی باگ. |
| درآمد جایاب | جمع `fee_amount` snapshotهای بازه منهای اصلاحیه‌های لغو |
| تفکیک منشأ پول رزروها | برای رزروهای بازه، `paid_by_gateway` و خرج‌های کیف پول به تفکیک منبع (شارژ شخصی، کارت هدیه، اعتبار سازمانی). بخش اعتبار سازمانی به «پول واقعی سازمان» و «تخفیف جایاب» تقسیم می‌شود، با نسبت `bonus_amount / amount` هر lot (تصویر کارفرما، بند ۱۷). |
| بدهی کیف پول | جمع موجودی `AVAILABLE` و `HELD` همهٔ حساب‌های قابل خرج: تعهد جایاب به کاربران. اعتبار منقضی‌شدهٔ بازه جدا نمایش داده می‌شود. |

**Panel:** برگهٔ «گزارش» در `Panel/app/settlements/page.tsx` با انتخاب بازهٔ جلالی و دکمهٔ دریافت Excel.

## HW-7.3 — ماسک شبا در لاگ فعالیت ادمین

`Back/src/common/interceptors/transform.interceptor.ts` بدنهٔ کامل هر درخواست غیر GET ادمین را در `admin_activities.body` ذخیره می‌کند (خطوط ۳۸ تا ۵۵). قبل از `prisma.adminActivity.create`، `body` و `param` از همان `maskSensitive` (HW-2.7) عبور کنند. کلیدهای `iban`، `account_number`، `tracking_code`، `iban_enc` و `account_no_enc` در هر عمقی ماسک شوند.

تست واحد: بدنهٔ `{ iban: 'IR05…9012', allocations: [...] }` با شبای ماسک‌شده ذخیره شود و بقیهٔ فیلدها دست‌نخورده بمانند.

## HW-7.4 — آمادگی برای تسویهٔ خودکار در آینده

سند می‌خواهد سیستم برای «اتصال API تسویه در آینده» آماده باشد. نکته‌هایی که این آمادگی را حفظ می‌کنند (کد اضافه‌ای لازم نیست):
- `Settlement` مستقل از روش واریز است. واریز خودکار فقط `created_by` را SYSTEM و `tracking_code` را شناسهٔ API می‌گذارد.
- ورود و خروج مبلغ فقط از `WalletService.move` انجام می‌شود.
- تأیید بانکی (`confirm`) جدا از ثبت (`POST`) است و می‌تواند بعداً با webhook بانک صدا زده شود.

اتصال واقعی به API بانک در این بسته ساخته نمی‌شود.
