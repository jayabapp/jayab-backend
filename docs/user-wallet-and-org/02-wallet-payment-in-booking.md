# ۰۲ — پرداخت رزرو با کیف پول (Back + Front)

**وابستگی:** RS-03 (پرداخت درگاهی رزرو) و OW-01.
**خروجی:** endpoint پرداخت رزرو (RS-3.1) با «استفاده از کیف پول». شامل برنامهٔ خرج بر اساس منبع و آگهی، کنار گذاشتن موجودی در مهلت ۱۰ دقیقه، پرداخت کامل از کیف پول بدون درگاه یا ترکیبی، ثبت در snapshot، و UI پرداخت تفکیکی در Front.

**قاعدهٔ اصلی:** فلوی رزرو تغییری نمی‌کند. شامل جواب ۱ یا ۲ میزبان، وعدهٔ ۲۱ دقیقه، پیگیری پشتیبان، مهلت پرداخت ۱۰ دقیقه، قفل تاریخ، طلب ۸۰٪ میزبان و لغو طبق قانون کنسلی. فقط منبع پول مهمان عوض می‌شود.

---

## OW-2.1 — کدام پول روی کدام آگهی

`WalletService.spendable(userId, { mode, reserve })` برنامهٔ خرج را برمی‌گرداند. شرط هر منبع (E4):

| منبع | قابل خرج روی | شرط حالت ورود |
| --- | --- | --- |
| `EMPLOYEE_ORG_CREDIT` | آگهی‌های مجاز سازمان (`isOrgEligibleProperty`، OW-4.1). **به وضعیت سازمان، وضعیت کارمند و `ORG_PLAN_ENABLED` وابسته نیست**، چون اعتبار شارژشده حکم هدیه دارد و تا انقضا قابل خرج است (E9). | فقط `mode = ORG` |
| `USER_GIFT` | `jayab_booking = true` و `is_authorized = true` | ORG (اگر سازمان «پرداخت ترکیبی» دارد) و PERSONAL |
| `USER_TOPUP` | `jayab_booking = true` | ORG (اگر سازمان «پرداخت ترکیبی» دارد) و PERSONAL |
| درگاه | همه | PERSONAL همیشه. ORG فقط با «پرداخت ترکیبی» سازمان. |

- `mode` از حالت ورود کارمند می‌آید (OW-07). کاربر عادی همیشه `PERSONAL` است.
- اگر در `mode = ORG` اعتبار سازمانی کافی نیست و سازمان «پرداخت ترکیبی» ندارد، پرداخت ممکن نیست. پیام: «اعتبار سازمانی شما برای این رزرو کافی نیست.»

## OW-2.2 — ترتیب خرج (E3)

- **داخل هر منبع:** lotها به ترتیب زودترین `expires_at` خرج می‌شوند. lot بدون انقضا آخر است و بین lotهای هم‌انقضا قدیمی‌تر اول است.
- **ترتیب منبع‌ها:** `EMPLOYEE_ORG_CREDIT` (در ORG)، بعد `USER_GIFT`، بعد `USER_TOPUP`، بعد درگاه.
- **کاربر می‌تواند** در صفحهٔ پرداخت «استفاده از کیف پول» را خاموش کند (فقط PERSONAL). در ORG، اعتبار سازمانی همیشه اول خرج می‌شود.

تابع خالص `buildSpendPlan(lots, amount, rules)` در `Back/src/wallet/common/spend-plan.ts` با تست کامل:
- مرز موجودی، چند lot با انقضای مختلف
- آگهی غیرمجاز برای کارت هدیه، ORG بدون ترکیبی
- جمع برنامه دقیقاً برابر مبلغ

## OW-2.3 — endpoint پرداخت

گسترش `POST /api/v1/reserves/:id/pay` (RS-3.1). پیش‌شرط‌ها همان RS-3.1 هستند (وضعیت ۴۰ یا ۷۰ و مهلت باقی).

```ts
class PayPropertyReserveUserDto {
  redirect_url: string;
  gateway?: PaymentGatewayEnum;
  use_wallet?: boolean;            // default true
}
// result:
//   { status: 'PAID' }                                    when the wallet covers everything
//   { status: 'REDIRECT', payment_url, wallet_part, gateway_part }
```

- **`GET /api/v1/reserves/:id/pay-preview`** همان برنامه را بدون تغییر برمی‌گرداند: `{ amount, parts: [{ source, organization?, amount }], gateway_part, mode }`. Front از این برای نمایش استفاده می‌کند.
- **در یک تراکنش:**
  1. اگر برای همین رزرو موجودی `HELD` قبلی هست (تلاش قبلی)، اول `releaseHold` اجرا می‌شود.
  2. `buildSpendPlan`. برای هر جزء، `move(AVAILABLE → HELD)` با کلید `reserve:{id}:hold:{lotId}:{attempt}`.
  3. `Payment` با `amount = کل`، `pay_by_wallet` و `pay_by_gateway` ساخته می‌شود. این ستون‌ها از قبل در مدل هستند.
     - اگر `gateway_part = 0`: `type = TurnoverType.PAY_RESERVE_BY_WALLET` (از قبل در enum هست) و `status = APPROVED`.
     - در غیر این صورت: `PAY_RESERVE` و ساخت لینک درگاه فقط برای `gateway_part`.
- **پرداخت کامل از کیف پول:** بعد از تراکنش، همان `ReservePaymentService.onPaid(payment, walletParts)` (RS-3.2) فوراً صدا زده می‌شود. نتیجه `PAID` است.
- **پرداخت ترکیبی:** کال‌بک درگاه `onPaid` را صدا می‌زند و `onPaid` اول `capture` می‌کند (`HELD → SPENT` با کلید `reserve:{id}:spend:{lotId}`).
- **شکست یا انقضا:** درگاه ناموفق یا رسیدن مهلت ۱۰ دقیقه (تیک RS-2.6 برای ۴۰ و ۷۰) `releaseHold` را صدا می‌زند (`HELD → AVAILABLE`، کلید `reserve:{id}:release:{lotId}:{attempt}`). پس موجودی هرگز در `HELD` گیر نمی‌کند.
- **تعارض در کال‌بک (۱۳۰):** موجودی `HELD` آزاد می‌شود و فقط سهم درگاه به `GuestRefund` می‌رود.

## OW-2.4 — تکمیل `onPaid` و snapshot

- `onPaid(payment, walletParts)` قبل از `recordReserveCredit`، `capture` را برای بخش‌های `HELD` همین رزرو اجرا می‌کند. snapshot مقدارهای `paid_by_gateway` و `paid_by_wallet` را دارد (HW-2.4).
- **سهم میزبان** همان ۸۰٪ کل قیمت است.
- اگر بخشی از پرداخت اعتبار سازمانی بوده، `reserve` یک فیلد محاسبه‌شدهٔ `organization_id` در خروجی پشتیبانی دارد تا برچسب «سازمانی» نمایش داده شود (RS-5.6). ستون جدید لازم نیست، چون از ردیف‌های SPENT خوانده می‌شود.

## OW-2.5 — UI پرداخت (Front)

در کارت رزرو مهمان (RS-4.4)، دکمهٔ «پرداخت و قطعی کردن رزرو» یک sheet باز می‌کند:
- **مبلغ کل** و **تفکیک** از `pay-preview`: «اعتبار سازمانی {سازمان}: X»، «کارت هدیه: Y»، «کیف پول شخصی: Z» و «پرداخت آنلاین: W».
- **سوئیچ «استفاده از کیف پول جایاب»** در حالت PERSONAL. با تغییر آن، preview دوباره گرفته می‌شود.
- اگر `gateway_part = 0`: دکمهٔ «پرداخت با کیف پول» و بعد از موفقیت، همان کارت «رزرو قطعی» بدون رفتن به درگاه.
- اگر کیف پول دارد ولی آگهی برای آن منبع مجاز نیست، یک خط توضیح نمایش داده شود. نمونه: «اعتبار کارت هدیه فقط روی اقامتگاه‌های احرازشدهٔ رزرو با جایاب قابل استفاده است.»
- شمارندهٔ ۱۰ دقیقه بالای sheet هم نمایش داده می‌شود.
- **کدهای خطای جدید** در `apiErrors` (XC-2): `WALLET_INSUFFICIENT_ORG_CREDIT`، `WALLET_SOURCE_NOT_ALLOWED` و `WALLET_PLAN_CHANGED` (موجودی بین preview و پرداخت تغییر کرده است. preview دوباره نمایش داده و تأیید دوباره خواسته شود).
- namespace `wallet`، سه زبان و دو تم (XC-4).

## حالت‌های مرزی

| حالت | رفتار |
| --- | --- |
| کاربر دو تب باز کرده و هر دو را پرداخت می‌کند | تلاش دوم ابتدا hold اول را آزاد می‌کند و بعد دوباره hold می‌کند. فقط یک پرداخت `INIT` معتبر است (RS-3.1، خطای 409). |
| lot در میانهٔ پرداخت منقضی می‌شود | `HELD` منقضی نمی‌شود (HW-2.6). اگر پرداخت شکست بخورد، بعد از آزادسازی در اجرای بعدی cron منقضی می‌شود. |
| کارمند غیرفعال‌شده | اعتبارش تا انقضا قابل خرج است (E9) |
| سازمان غیرفعال‌شده | اعتبار موجود کارکنان روی آگهی‌های مجاز همچنان خرج می‌شود. فقط شارژ جدید ممکن نیست. |
| آگهی از فهرست مجاز حذف شده یا دیگر `jayab_booking` نیست | در زمان `pay` چک می‌شود. منبع سازمانی خرج نمی‌شود و پیام `WALLET_SOURCE_NOT_ALLOWED` برمی‌گردد. |
| لغو بعد از پرداخت | HW-6.6: سهم کیف پول به همان حساب‌ها برمی‌گردد |
