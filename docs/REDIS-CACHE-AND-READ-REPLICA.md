# تحلیل Redis Cache و Read Replica

این سند نتیجه‌ی بررسی کد فعلی بک‌اند (`feat/new-app`) درباره‌ی دو موضوع است: آیا کش Redis درست استفاده شده، و آیا به Read Replica نیاز داریم. بخش اول (فاز ۱) پیاده‌سازی و تست شده. بخش دوم یک تصمیم زیرساختی بزرگ‌تر است که پیش از هر پیاده‌سازی به داده‌ی واقعی نیاز دارد.

## خلاصه

| | وضعیت فعلی | نیاز به کار |
|---|---|---|
| Redis برای صف کار (Bull)، محدودیت نرخ لاگین، کش JWT | ✅ درست وصل و استفاده شده | خیر |
| Redis برای کش HTTP جواب کنترلرها (`@CacheInterceptor`) | ✅ **انجام شد** — فاز ۱ را ببین | خیر — تست dev/QA قبل از انتشار باقی مانده |
| Read Replica برای Postgres | ❌ اصلاً وجود ندارد | فقط اگر متریک واقعی نیاز را نشان دهد؛ الان زود است |

## ۱. Redis همین الان کجا درست کار می‌کند

- **صف کارها (Bull):** پیامک ثبت‌آگهی، پیامک پرداخت، شمارش بازدید و لاگ تماس همه از طریق `BullModule` روی همین Redis اجرا می‌شوند (`src/app.module.ts`, `src/chat/shared-chat.service.ts`, `src/payment/roles/user/user.controller.ts`, `src/property/roles/user/user.controller.ts`).
- **محدودیت نرخ لاگین:** `src/auth/guards/auth-throttler.guard.ts` مستقیم با `ioredis` عدد تلاش‌های ورود را نگه می‌دارد.
- **کش JWT/پروفایل کاربر:** `src/auth/strategies/user.strategy.ts` نتیجه‌ی decode شده را ۶۰ ثانیه در Redis نگه می‌دارد تا هر درخواست به دیتابیس نزند.
- **یک کش دستی در جست‌وجوی ملک:** `src/property/roles/user/user.service.ts` (خط ۳۵۴ و ۳۸۵) یک نتیجه را با کلید ثابت و TTL یک‌ساعته مستقیم در Redis می‌گذارد.
- **پاک‌کردن کش اطلاعات تماس مالک:** `src/property/roles/owner/owner.service.ts` خط ۴۴۷.

این پنج مورد همگی درست و هدفمند Redis را به‌کار می‌گیرند. مشکل جای دیگری‌ست.

## ۲. مشکل: کش HTTP کنترلرها روی Redis نیست

سیزده کنترلر از `@CacheInterceptor` + `@CacheTTL` استفاده می‌کنند تا جواب یک endpoint را چند دقیقه نگه دارند:

```
banner, city (user+admin), category, landing-page, property-option,
subscription-plan, advisor, auth (user), content (shared), dashboard (admin),
redirect-url, setting (shared)
```

اما ماژولی که این interceptor به آن وصل است، Redis نیست:

```ts
// src/app.module.ts
CacheModule.register({
  max: 1000,       // فقط ۱۰۰۰ آیتم، مشترک بین هر ۱۳ کنترلر
  isGlobal: true,
})
```

بدون آرگومان `store`، `@nestjs/cache-manager` به‌صورت پیش‌فرض از یک Map در حافظه‌ی همان پردازه‌ی Node استفاده می‌کند. یک کامنت در `src/common/utils/constants/cache-ttl.constant.ts` به پکیج `@tirke/node-cache-manager-ioredis` اشاره دارد، ولی این پکیج اصلاً در `package.json` نصب نیست — یعنی نقشه‌ی اصلی نیمه‌کاره رها شده.

### چرا این مهم است

1. **کش با هر deploy/ری‌استارت کاملاً خالی می‌شود.** درحالی‌که Redis زنده می‌ماند و بین ری‌استارت‌ها کش را حفظ می‌کند.
2. **اگر روزی بک‌اند روی بیش از یک نمونه (PM2 cluster، چند container) اجرا شود، هر نمونه کش جدای خودش را دارد.** یعنی به‌جای یک کش مشترک، N برابر حافظه مصرف می‌شود و هر نمونه به‌طور جدا اولین درخواست‌هایش را از دیتابیس می‌گیرد. الان که ظاهراً تک‌نمونه‌ای اجرا می‌شود ضرر عملی ندارد، ولی هر مقیاس‌گیری افقی در آینده این مشکل را فعال می‌کند.
3. **سقف ۱۰۰۰ آیتم بین همه‌ی ۱۳ کنترلر مشترک است.** لیست شهرها، دسته‌بندی‌ها، صفحات لندینگ و... همه در یک استخر با هم رقابت می‌کنند؛ با رشد تعداد پارامترهای مختلف کوئری (هر ترکیب query string یک کلید جداست)، احتمال بیرون‌انداختن زودهنگام یک آیتم پرکاربرد به‌خاطر یک آیتم کم‌کاربرد بالا می‌رود.

### آیا الان روی سرعت اثر منفی دارد؟

نه به‌صورت مستقیم — چون فعلاً ظاهراً تک‌نمونه اجرا می‌شود، همان کش حافظه هم کار می‌کند. اما:
- بعد از هر deploy، چند دقیقه‌ی اول همه‌ی این ۱۳ endpoint دوباره باید از دیتابیس بخوانند (cold start).
- این داده‌ها (بنر، شهر، دسته‌بندی، لندینگ، تنظیمات، پلن‌ها) تقریباً ثابت‌اند و مرجع بسیاری از صفحات پرترافیک (از جمله لندینگ صفحه‌ی اصلی) هستند؛ نگه‌داشتن‌شان در Redis هزینه ندارد و فقط فایده دارد.

## ۳. Read Replica — نیاز فعلی: نه

- دیتابیس یک Postgres خودمیزبان است (نه یک سرویس ابری مثل Neon/RDS که replica را با چند کلیک اضافه می‌کند) — طبق `docs/NEW-APP-DEPLOYMENT.md` و env نمونه، یک `DATABASE_URL` واحد.
- فقط یک `PrismaService` با یک اتصال وجود دارد؛ هیچ مسیر خواندن/نوشتن جدایی در کد نیست.
- در migrationهای اخیر (`20260903120000_search_title_trigram_indexes`، `20260903150000_add_property_sort_indexes`، `20260904150000_add_landing_location_indexes`) تیم فعالانه روی کند بودن کوئری‌های جست‌وجو و مرتب‌سازی با **ایندکس** کار کرده — این معمولاً قدم درست‌تری نسبت به Read Replica است، چون هزینه‌اش صفر (فقط دیسک) و بدون پیچیدگی replication lag است.
- من به متریک واقعی سرور (CPU دیتابیس، تعداد کانکشن هم‌زمان، کندترین کوئری‌ها) دسترسی ندارم؛ بدون این داده نمی‌توان گفت دیتابیس واقعاً زیر فشار IO/CPU است یا نه.

### نتیجه

راه‌اندازی Read Replica یک تصمیم زیرساختی جدی است: به یک سرور Postgres دوم، پیکربندی replication، مانیتور lag، و مسیریابی کوئری خواندن/نوشتن در کد نیاز دارد. اگر بدون شواهد فشار واقعی این کار انجام شود، فقط هزینه و پیچیدگی عملیاتی اضافه می‌کند بدون فایده‌ی اثبات‌شده. **پیشنهاد: فعلاً نه.** به‌جایش:

1. اول تکمیل کش Redis (بخش بعدی) را انجام بده — فشار خواندن روی دیتابیس را کم می‌کند بدون هیچ زیرساخت جدید.
2. یک هفته پایش کن: CPU/IO سرور Postgres در ساعت پیک، تعداد کانکشن هم‌زمان (`SELECT count(*) FROM pg_stat_activity;`)، و ۱۰ کوئری کندتر (`pg_stat_statements` اگر فعال است).
3. اگر بعد از کش، CPU دیتابیس در ساعت پیک بالای ۷۰-۸۰٪ ماند یا کانکشن‌ها به سقف نزدیک شدند، همین سند را برای فاز ۲ (Read Replica) گسترش بده.

## فاز ۱ — انجام شد: کش Redis برای `@CacheInterceptor`

**وضعیت: پیاده‌سازی و تست شده روی `feat/new-app`.** این بخش دیگر پلن نیست، مستند چیزی‌ست که در `src/app.module.ts` اعمال شده.

### هدف

بدون تغییر رفتار endpointها یا مقادیر TTL، store کش HTTP از حافظه‌ی پردازه به همان Redis موجود منتقل شد. کلید و منطق invalidation تغییری نکرده (الان هم بر پایه‌ی TTL است، بدون invalidation فعال — این فاز آن را تغییر نداد).

### پیش‌نیاز و انتخاب نسخه

```bash
yarn add cache-manager-ioredis-yet@1.2.2
```

**نسخه‌ی دقیق مهم است.** آخرین نسخه‌ی این پکیج (`2.x`) به API مبتنی‌بر Keyv مخصوص `cache-manager@6+` سوییچ کرده و با `cache-manager@5.7.6` نصب‌شده در این پروژه (پشت `@nestjs/cache-manager@2.3.0`) تایپ‌هایش جور در نمی‌آید — تلاش اول با `2.1.2` بود که با خطای تایپ در `tsc` رد شد. نسخه‌ی `1.2.2` هنوز به `cache-manager: ^5.2.3` وابسته است و با نسخه‌ی نصب‌شده جور است. پکیج `@tirke/node-cache-manager-ioredis` که در کامنت قدیمی بود اصلاً نصب نبود؛ استفاده نشد.

### تغییرات کد

**۱. `src/app.module.ts`** — `CacheModule.register` جای خودش را به `CacheModule.registerAsync` با store ioredis داد:

```ts
import { CacheModule, type CacheStore } from '@nestjs/cache-manager';
import { redisStore } from 'cache-manager-ioredis-yet';

// ...

CacheModule.registerAsync({
  isGlobal: true,
  inject: [ConfigService],
  useFactory: async (config: ConfigService) => ({
    store: (await redisStore({
      host: config.get('redis.host'),
      port: config.get('redis.port'),
      password: config.get('redis.password'),
      keyPrefix: process.env.IS_SANDBOX == '1' ? 'sandbox:jayab:cache:' : 'jayab:cache:',
    })) as unknown as CacheStore,
  }),
}),
```

نکته‌ی مهم: `keyPrefix` جدا از prefix چیزهای دیگر (`jayab:`, صف‌های Bull) است تا یک `FLUSHDB` یا پاک‌سازی دستی کش، صف‌ها یا نشست‌های دیگر را پاک نکند.

**نکته‌ی cast:** `@nestjs/cache-manager` به‌جای import کردن نوع `Store` از خود پکیج `cache-manager`، یک اینترفیس `CacheStore` مینیمال و مستقل تعریف کرده. `RedisStore` (خروجی `redisStore`) ساختاری همان چیزی‌ست که `CacheStore` نیاز دارد (`get`/`set`/`del`) و در تست واقعی هم دقیقاً همین‌طور رفتار کرد، ولی چون دو اینترفیس جدا تعریف شده‌اند `tsc` نمی‌تواند این را خودش تشخیص بدهد؛ `as unknown as CacheStore` فقط همین شکاف تایپی را می‌بندد، رفتار runtime را تغییر نمی‌دهد.

**۲. حذف سقف `max: 1000`** — دیگر لازم نبود؛ Redis خودش TTL را مدیریت می‌کند. اگر نگران حجم Redis هستی، `maxmemory-policy allkeys-lru` را روی خود سرور Redis تنظیم کن، نه در کد.

**۳. بدون تغییر در ۱۳ کنترلر** — چون `@CacheInterceptor` و `@CacheTTL` مستقل از store کار می‌کنند، هیچ فایل کنترلری نیاز به تغییر نداشت.

### تستی که واقعاً انجام شد

- `tsc --noEmit` و `eslint` روی `src/app.module.ts` تمیز پاس شدند (هیچ خطا یا هشدار جدیدی نسبت به قبل).
- یک اسکریپت یک‌بارمصرف (`scripts/verify-redis-cache-store.ts`, بعد از تست حذف شد) دقیقاً همان فراخوانی `redisStore(...)` را با همان آرگومان‌ها، روی سرویس Redis محلی (`docker-compose.local.yml`, پورت ۵۶۳۷۹) اجرا کرد:
  - `set()` → `get()` مقدار را درست برگرداند.
  - کلید خام در Redis زیر همان `jayab:cache:` ساخته شده بود (نه چیز دیگری).
  - TTL روی کلید درست ثبت شده بود (`PTTL` بازه‌ی انتظار را نشان داد).
  - `del()` کلید را واقعاً از Redis حذف کرد.
- این یعنی خود store — نه فقط تایپ‌ها — با آرگومان‌های واقعی پروژه تست شده. تست بوت کامل اپلیکیشن (با Postgres/S3/Firebase/SMS واقعی) در این‌جا انجام نشد؛ توصیه می‌شود روی محیط dev/QA یک بار `yarn start:dev` بالا بیاید و طبق چک‌لیست زیر تایید بشود.

### تست پیشنهادی روی dev/QA قبل از انتشار در production

- `yarn start:dev` بالا بیاید و یکی از endpointهای کش‌شده (مثلاً `/city` یا `/banner`) دو بار پشت‌سرهم صدا زده شود؛ با `redis-cli --scan --pattern 'jayab:cache:*'` باید کلید ساخته‌شده دیده شود.
- سرور را ری‌استارت کن و همان endpoint را دوباره صدا بزن — چون کش در Redis است، نباید کوئری تازه به دیتابیس برود (با لاگ Prisma یا `pg_stat_statements` قابل تایید است).
- مطمئن شو کلیدهای کش با کلیدهای صف Bull یا throttler قاطی نشده‌اند (`redis-cli --scan --pattern 'jayab:*' | sort | head -50`).

### ریسک و محدودیت شناخته‌شده (بدون تغییر نسبت به وضعیت فعلی)

- کش هنوز TTL-محور است؛ وقتی ادمین یک بنر/شهر/تنظیمات را در پنل عوض می‌کند، تا پایان TTL (۳ تا ۵ دقیقه) کاربر نسخه‌ی قدیمی را می‌بیند. این رفتار همان چیزی‌ست که الان هم با کش حافظه وجود دارد — این فاز آن را بدتر یا بهتر نمی‌کند، فقط کش را قابل‌اشتراک و پایدار بین ری‌استارت‌ها می‌کند.
- اگر بعداً خواستی invalidation فوری (پاک‌کردن کش دقیقاً وقتی ادمین ذخیره می‌زند) اضافه کنی، آن یک فاز جداست: در سرویس‌های admin مربوطه بعد از هر `update`/`create` یک `cacheManager.del(key)` یا `cacheManager.store.keys('pattern:*')` + پاک‌سازی دسته‌ای اضافه می‌شود. پیشنهاد می‌کنم این را فقط برای بنر و تنظیمات (چیزهایی که ادمین انتظار تغییر آنی دارد) در فاز بعدی انجام بدهی، نه همه‌ی ۱۳ مورد.

### تاثیر روی سرعت

- درخواست اول بعد از هر deploy یا اولین باری که یک ترکیب پارامتر خاص دیده می‌شود: بدون تغییر (باید از دیتابیس بخواند، دقیقاً مثل الان).
- درخواست‌های بعدی در بازه‌ی TTL: زمان پاسخ عملاً یکسان با کش حافظه (هر دو زیر ۱ میلی‌ثانیه برای یک GET ساده)؛ Redis این‌جا کندتر از حافظه‌ی محلی نیست چون Redis هم داخل شبکه‌ی محلی/همان سرور است.
- فایده‌ی واقعی در سرعت، در سناریوی deploy مکرر و مقیاس افقی آینده دیده می‌شود، نه در حالت فعلی تک‌نمونه.

## فاز ۲ (مشروط، فعلاً فقط برای مرجع) — Read Replica

این بخش را فقط وقتی باز کن که بعد از فاز ۱ و یک هفته پایش، عدد واقعی نشان داد دیتابیس اصلی زیر فشار است.

### معیار شروع

- CPU سرور Postgres در ساعت پیک بالای ~۷۰-۸۰٪ پایدار.
- `pg_stat_activity` نشان بدهد کانکشن‌ها مرتب به سقف نزدیک می‌شوند.
- کندترین کوئری‌های `pg_stat_statements` عمدتاً از نوع خواندن (SELECT جست‌وجوی ملک، لیست‌ها، گزارش‌ها) باشند، نه نوشتن.

### کارهای لازم (فقط سرفصل، جزئیات را بعد از تایید فاز شروع بنویس)

1. **تصمیم زیرساخت:** یک replica خودمیزبان با streaming replication روی همان سرور Postgres راه بیندازی، یا کل دیتابیس را به یک سرویس مدیریت‌شده (مثلاً Neon که این پروژه از قبل به آن دسترسی MCP دارد) کوچ کنی که replica را آماده می‌دهد. گزینه‌ی دوم پیچیدگی عملیاتی کمتری دارد ولی کوچ کردن دیتابیس یک پروژه‌ی جدا و پرریسک است.
2. **در Prisma:** یک `PrismaService` دوم یا یک wrapper که بر اساس نوع عملیات (خواندن/نوشتن) به `DATABASE_URL` یا `DATABASE_REPLICA_URL` وصل شود؛ Prisma به‌صورت native از چند datasource پشتیبانی نمی‌کند، پس این لایه باید دستی نوشته شود (یا از یک extension/middleware مثل `@prisma/extension-read-replicas` استفاده شود).
3. **مسیرهایی که باید به replica بروند:** فقط کوئری‌های خواندن با تحمل کمی تاخیر — لیست/جست‌وجوی ملک، صفحات لندینگ، گزارش‌های ادمین. مسیرهایی که بلافاصله بعد از نوشتن باید بخوانند (مثلاً بعد از ثبت رزرو، تایید موجودی) باید از دیتابیس اصلی بخوانند تا replication lag باعث نمایش داده‌ی قدیمی نشود.
4. **مانیتورینگ lag:** قبل از فعال‌شدن در production باید هشدار روی replication lag تنظیم شود.

### تاثیر روی سرعت (اگر لازم شد)

مثبت برای کوئری‌های سنگین خواندن در ساعت پیک، چون بار بین دو سرور پخش می‌شود. اما اگر مسیر خواندن/نوشتن درست تفکیک نشود، ریسک نمایش داده‌ی چند ثانیه قدیمی (replication lag) به‌خصوص در صفحه‌ی جزئیات ملک بعد از رزرو وجود دارد — دقیقاً همان‌جایی که این پروژه به‌خاطر باگ idempotency رزرو (migration اخیر) حساسیت بالایی رویش دارد.

## جمع‌بندی

- **انجام شد:** فاز ۱ (اتصال `@CacheInterceptor` به Redis) — کد در `src/app.module.ts`، تست شده با یک اتصال واقعی به Redis. قبل از commit فقط چک‌لیست «تست پیشنهادی روی dev/QA» باقی مانده.
- **الان نساز:** فاز ۲ (Read Replica). اول یک هفته پایش کن، بعد با عدد واقعی برگرد سراغ این سند.
